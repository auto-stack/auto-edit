# auto-edit 北极星战略 v2（2026-09-21）

> 状态：**现行基线**（v1 被 v2 取代，v1 存档于 `001-north-star.md`）。
> 本文是产品与架构的战略层决策记录，供后续所有 auto-plan 计划对齐引用；
> 修订走追加（v3+），不回改历史版。

## v1 → v2 变更记录（用户五条裁定）

1. **剥离协作倾向**：Zed 数据结构为多人实时协同设计；auto-edit 不需要
   （AI 时代真正的编辑经 agent 命令发生，编辑器大部分时候是**看**代码，
   至多单人编辑）→ §4.2 内核课重写：要 rope 的性能，不要协作的复杂度；
   确立 **viewing-first** 优先级。
2. **补全/重型语言服务出局**：rust-analyzer 类服务 2GB 内存 + CPU 打断
   体验，AI 时代得不偿失 → 移出 L 线，进裁剪宪法；语义导航交给 agent
   或按需外部工具。
3. **编码降维**：Win11 下中文文本已 UTF-8 为主流 → M 线只做 UTF-8
   （含 BOM 与无损兜底），GBK 移出生死线、列为非目标。
4. **agent 交互定位修正**：auto-edit 是**工具**，不成长为独立 agent
   （那是 auto-musk 的位）→ 砍掉 v1 的 ACP 搭载面（editor-as-client），
   收敛为**被驱动**（tool use）+ **被嵌入**（编辑页组件化/Blueprint 化
   共享给 auto-musk 等）。
5. **新增中期战场：diff 对打 Beyond Compare** → M 线新增 M3 阶段，
   diff 引擎入内核，长期审阅面复用同一引擎。
6. **同日补注（"过早优化"质询的裁定）**：(a) 确认缓冲区类预算（100MB/
   1GB/diff）在内核 rope 化前**架构性不可达**，此前**禁止**对该路径做
   任何调优——那才是过早优化；bench 在此之前只记基线并标"架构阻塞"，
   其真正价值是启动链归因分解与 rope 落地后的前后对照。(b) §2.1 预算表
   补**解锁条件**列——每项预算标明被哪个地基门控（rope / exe 打包 /
   diff 引擎），防止向错误的层讨账。(c) M1 排序改为**上游地基供料
   先行**（rope/delta/分块读立即立上游计划，前置时间最长），bench 与
   本仓去镜像先行段并行。(d) §5 门禁分两档：启动/首帧类"产品身份"
   指标硬门禁（回归当天修），其余指标 M2/M3 记账、M4 统一收口——
   微优化集中在功能冻结后。
7. **同日补注二（性能模式与测量效力分级）**：性能模式 = a2r 转译 +
   release 编译 + RQ 模式（外部统一渲染器做 compositor，app 只起自身
   逻辑；预热渲染器后单实例启动快、内存小），但修改→结果周期很长，
   **只适合发布前/里程碑测试**。裁定：(a) §5 立**测量模式阶梯**——预算
   与门禁只在 L2 性能模式的数字上评估，日常开发用代理指标防结构回归；
   (b) RQ+预热渲染器不只是测量配置，更可能是**交付拓扑候选**（渲染成本
   跨实例摊销 = notepad 高频开关场景的稳态秒开），与 exe 路径联合入 Q2
   裁定；(c) 预算语义拆分：稳态启动（渲染器暖态）为头条指标，渲染器
   冷启动一次性成本单列；(d) 性能模式须一键脚本化（`tools/perf/`），
   "启动复杂"是一次性工具债。
8. **同日补注三（M1 性能轨内部排序，用户四步裁定）**：① **基本功能
   正常**（矩阵稳定/双轨健康——性能模式测试时不陷于"改代码才跑得
   起来"，长周期下每次测量会话退化成调试会话不可接受）；② **性能模式
   一键化**（`tools/perf/` 自动切换 a2r+release+RQ）；③ **建立测量
   体系**（bench + 阶段插桩 + 预算断言）；④ **才开始性能测试**（首份
   L2 基线报告）。注意 ① 在性能模式语境下含硬上游依赖：a2r F-R1 未解
   则性能模式根本跑不通——故上游供料包（F-R1 + F-RV6 + rope/delta/
   分块读）仍为 M1 第一优先、与①并行。

## 0. 摘要

auto-edit 的北极星：**AI 时代的轻量高性能文本工作台**——编辑器大部分
时候用来**看**代码（浏览、比对、审阅），批量编辑经 agent 的结构化命令
发生，人只做小步精修与取舍；编辑器本体是**工具**（被 agent 驱动、被
其他应用嵌入），不是 agent 宿主。中期（M 线）以可量化的性能预算打赢
Notepad++ 对位，并以 diff 引擎对打 Beyond Compare；长期（L 线）以
「被驱动 + 被嵌入」的工具形态成为 AI 生态里的标准编辑组件，而不是
复刻 VSCode 的功能广度。

## 1. 产品哲学：AI 时代编辑器的角色反转

### 1.1 为什么"精简"是对的

VSCode 的重量来自它的历史使命：**人是唯一的编辑者**。所以它需要插件市场
补齐人的短板（snippet 体系、补全引擎、重构菜单、格式化器、调试器集成）。
AI 时代这个前提反转了：批量编辑、重构、跨文件改动、样板代码——这些恰好
是插件/功能所服务的场景——都交给了 agent。编辑器的职责收缩为
"让人看、让人比、让人挑、让人小修"。

由此确立两条第一性原则：

- **Viewing-first（看优先于写）**：打开/滚动/搜索/比对的优先级高于
  编辑路径的复杂度。性能预算首先花在看；编辑器要经得起"当阅读器用"。
- **编辑器是工具，不是 agent**：agent 的人格、编排、决策是 auto-musk
  的事；auto-edit 提供最好的"被驱动的编辑面"和"可嵌入的编辑组件"，
  自己不长 agent 能力。

### 1.2 保留清单（人在 AI 时代仍必须自己做的事）

1. **打开任何文件都快** —— 日志、配置、数据文件、上百 MB 的转储；文件级
   而非工程级入口（这是 Notepad++ 的本体，不是 VSCode 的本体）。
2. **小步精修** —— 手比 agent 快的场景：改一个值、挪一行、改错别字。
   键入延迟必须低于感知阈值。
3. **比对与审阅** —— 文件/目录 diff（对打 Beyond Compare 的本体）、
   agent 修改以 diff 到达后人的逐块取舍（接受/拒绝/修改后再接受）。
4. **上下文投喂** —— 选中"给 agent 看什么"（文件/选区/目录），是人的
   判断，不是 agent 的。
5. **即席记录** —— notepad 本体：scratch、临时粘贴、快速笔记。
6. **安全感** —— 会话恢复、自动存盘、checkpoint（"AI 改坏之前长什么样"）。

### 1.3 裁剪清单（明确不做，写进宪法）

- **插件市场 / 第三方扩展生态**。配置面用 config-as-data（键位/外观/行为
  均为数据文件，已有 OS 键位层先例）。远期若确需扩展面，WASM 沙箱是
  唯一可接受形态，但不是承诺。
- **自动补全与重型语言服务内置**（v2 新增）。rust-analyzer 类服务
  2GB 内存 + 常态 CPU 打断，在 AI 时代得不偿失。语法高亮用 tree-sitter
  （廉价、增量、随内核走）；精确语义导航（定义跳转/引用）交给 agent
  或按需手动挂外部工具。**补全是 agent 的事。**
- **snippet/模板体系、重构工具菜单、可视化设计器**。同上，是 agent 的活。
- **远程开发/容器/SSH 工作区**。agent 在哪里跑是 agent 侧的事。
- **多人协同编辑 / CRDT / OT**。Zed 的协作投入服务多人实时编辑；
  auto-edit 的并发问题是"人 vs agent"，用结构化编辑事务 + checkpoint
  解决。单写者模型，不需要合并多个编辑流。
- **agent 宿主能力**（v2 收紧）：不做 agent 面板、不做 agent 市场、
  不内置模型对话。auto-edit 不搭载 agent，只被 agent 使用。
- **vim 仿真、深度主题市场**。抢存量用户的打法，不是我们的阶段。

### 1.4 竞争定位

| | Notepad++ | VSCode | Zed | **auto-edit** |
|---|---|---|---|---|
| 启动/轻量 | 好（C++/Win） | 差（Electron） | 中（快但重于 NP++） | **目标：最优** |
| 大文件 | 好 | 差 | 中 | **目标：最优** |
| diff/比对 | 无（靠插件） | 弱 | 中 | **目标：对打 Beyond Compare** |
| 平台 | Win only | 全 | 全（2025-10 起 Win 正式支持） | **Win first** |
| 定位轴 | 文件瑞士军刀 | 人写代码的 IDE | 人写代码的 IDE + 协作 | **看/比/小修的工作台** |
| agent 关系 | 无 | 靠插件/分叉绑定自家 | ACP 搭载（BYO agent） | **被 agent 驱动 + 被嵌入（纯工具）** |
| 技术栈 | Scintilla/Win32 | Electron/TS | Rust/GPUI | **AutoLang/iced+wgpu/内核 Rust** |

一句话：**不和 Zed 抢"工程 IDE"，和 Notepad++ 抢"文件入口"、和 Beyond
Compare 抢"比对"，用 Zed 的工程方法（不是它的功能面）做到性能最优，
以纯工具定位接入 agent 生态（auto-musk 为首）。**

## 2. 中期目标（M 线）：替代 Notepad++ + diff 对打 Beyond Compare

"性能最好、启动最快、最流畅"必须是可以**被测出来并公开复现**的，否则只是
口号。M 线的第一件事就是立性能预算与基准设施（§5），然后逐项对位。

### 2.1 性能预算（2026 硬件参照：NVMe + 中端 CPU）

| 指标 | 预算 | 参照 | 解锁条件（地基） |
|---|---|---|---|
| 稳态启动到可输入（RQ 渲染器已预热，空窗口） | ≤ 80 ms | NP++ 每次全量约 150–300 ms | RQ 模式 + 预热渲染器 + exe 路径（Q2）+ 启动链瘦身（bench 分解供归因）——**头条指标** |
| 渲染器冷启动（登录/首启一次性） | 单列，预算随 Q2 拓扑定 | — | Q2（bundled iced vs RQ 常驻渲染器） |
| 热启动（会话恢复，懒装载） | ≤ 120 ms | 恢复 20 tab 不读盘 | 同上 + 会话懒装载（M2） |
| 打开 100 MB 文本 | ≤ 1 s，滚动不掉帧 | NP++ 约数秒；VSCode 基本不可用 | 内核 rope 化 + 分块读（上游）——**rope 前架构性不可达，禁调优** |
| 打开 1 GB 日志 | 可打开（分块/mmap 流式） | 多数编辑器放弃 | 同上 + 流式装载 |
| 键入到上屏 | ≤ 1 帧（16 ms，120 Hz 下 8 ms） | 感知阈值内 | 内核帧时间戳插桩（上游小供料）——测量本身待供料 |
| 滚动帧率 | 满刷新率（120 Hz 面板跑满） | 内核已做视口切片（Plan 629） | 小文件已解；大文件满帧率需 rope |
| 100 MB 文件全量 diff 出结果 | ≤ 2 s | BC 同量级或更快 | diff 引擎（M3） |
| 空闲内存（app 实例） | ≤ 60 MB | NP++ 约 20–50 MB | rope 化（去整串镜像）+ exe 打包；共享渲染器进程单列，预算随 Q2 |
| 安装包 | ≤ 15 MB 单 exe，无运行时依赖 | 对位 NP++ 的"绿色" | 独立 exe 路径（Q2） |

预算未达标的功能**不发布**——性能是发布门槛（M4 生效），不是优化项。
（viewing-first：前三条预算优先级最高。rope 前缓冲区类指标只记基线。）

### 2.2 Notepad++ 对位功能清单（M2 验收面）

必做（缺一即不算"替代"）：
- [ ] 编码：**UTF-8 为唯一支持面**（v2 裁定：Win11 时代中文文本已 UTF-8
      主流）——含/不含 BOM 读写、保留原 BOM 形态；对非法 UTF-8 文件
      **无损兜底**（提示后以替换符查看或只读二进制态，绝不静默转码
      落盘破坏原文件）。GBK/GB18030 等传统编码列为**非目标**，真实
      需求出现再议。
- [ ] 行尾：CRLF/LF/CR 识别、状态栏显示、转换命令；保留原行尾保存
- [ ] 查找替换：正则、大小写、整词、转义，跨文件查找（find in files）
- [ ] 会话：退出/崩溃恢复 tab 集+光标+滚动位置（懒装载）
- [ ] 大文件：> 50 MB 进入大文件模式（关折行/懒语法/分块解码）
- [ ] Windows 集成：右键"用 auto-edit 打开"（已有 open_with 接收臂，
      PLAN-016 T-08）、文件关联（pac `opens` 已声明）、任务栏跳转列表
- [ ] 脏标记/退出确认（已有：alert-dialog 三选一，Plan 626 T-06）
- [ ] 多 tab 与最近文件（部分已有）
- [ ] 语法高亮：常见 20 语言起步（内核 tree-sitter 化后解锁，§4.2）

明确不做（NP++ 有但裁掉）：宏录制、FTP/SFTP、插件生态、MD5 工具箱类
"顺手塞进去"的功能、传统多编码支持。

### 2.3 diff 能力（M3 验收面，对打 Beyond Compare）

diff 是 v2 新增的中期主战场，引擎入内核（Rust），文件比对与 agent
审阅面（L 线）共用同一引擎：

- [ ] **文件 diff 完本体**：并排+内联两视图、行级 + **行内字符级**高亮、
      hunk 导航（下一处/上一处差异）、语法高亮联动、双栏同步滚动、
      差异侧直接编辑（编辑后即时重比）
- [ ] 算法：histogram/patience 优先（对齐行移动识别，语义贴近 BC
      使用感），大文件走分块并行
- [ ] **目录 diff v1**：递归比对、按状态过滤（新增/改/删/二进制）、
      基础同步动作（单向复制/删除）；双向同步向导列开放问题（§9-Q5）
- [ ] 三方合并（3-way merge）：开放问题（§9-Q5），BC 的深水区
- [ ] 十六进制比对：非目标（初期）

## 3. 长期目标（L 线）：AI 生态的标准编辑工具

### 3.1 工具形态：被驱动 + 被嵌入（v2 收敛，砍掉搭载面）

auto-edit 与 agent 的关系只有两种，且都是**工具位**：

- **被驱动（editor-as-tool）**：PLAN-003 的 back HTTP API + MCP 自动化面
  （`desktop_mcp.py` 已是雏形）长成 agent 驱动协议——外部 agent（首要是
  auto-musk）可以 open/read/**结构化 delta 写**/save/diff/查询状态。
  这是"真正的编辑经 agent 命令发生"的落点：**结构化编辑 API 是第一等
  公民**，比人敲键盘更高优先级的写路径（§4.3）。
- **被嵌入（editor-as-component）**：单页面编辑功能做成**高集成度组件**
  ——编辑页（buffer 视图 + 命令集 + 查找 + diff 视图）自包含，与 app
  壳（tab/菜单/会话）解耦，最终以 Blueprint/组件形态进 bps 池共享给
  auto-musk 等 agent 应用内嵌。auto-edit 本身则成为该组件的旗舰壳。

明确不做：agent 面板、agent 市场、模型对话、ACP client 搭载面
（v1 的 editor-as-client 方向作废——那是把编辑器做成 agent 宿主，
与工具定位相悖，且我们已有 auto-musk 承担该位）。

### 3.2 审阅面（review）：被驱动形态的自然长成

- agent 修改以**结构化 diff** 到达：逐 hunk 接受/拒绝/编辑后接受
  （复用 M3 diff 引擎，同一套视图）；
- checkpoint 时间线：agent 会话前自动打点，可整体回滚（依赖 back 的
  文件版本化；事务化编辑，不需要 CRDT）；
- 上下文投喂交互：把当前选区/文件/目录"交给"驱动方 agent。

### 3.3 长期仍裁掉的

工程 IDE 面的绝大部分维持 §1.3 裁剪。长期新增的只有：diff 审阅面、
被驱动协议扩容、编辑页组件化、tree-sitter 多语言高亮与**轻量符号索引**
（tree-sitter 语法树上的跳转/大纲，非语言服务）、工程搜索（ripgrep 式）。
**不内置任何 rust-analyzer 量级的语言服务**（宪法）。

## 4. 架构蓝图

### 4.1 分层（沿用现状，职责收紧）

```
┌────────────────────────────────────────────────┐
│ 应用层 auto-edit（本仓，specs/auto-edit）        │
│  壳: tab/菜单/会话/查找/diff 视图（.at）          │
│  编辑页组件: buffer 视图+命令集（自包含，可外嵌）  │
│  back: 文件/搜索/会话/结构化编辑 API（#[api]）    │
├────────────────────────────────────────────────┤
│ 编辑器内核（auto-lang/auto-ui 内，Rust）         │
│  code_editor_core: rope 化 buffer/增量/渲染      │
│  diff 引擎: histogram/行内字符级/目录比对（新）    │
├────────────────────────────────────────────────┤
│ 框架层：AutoUI(iced+wgpu) / AutoVM / a2r        │
│ 工具链：auto（编译/运行/生成）                    │
└────────────────────────────────────────────────┘
```

原则：**热路径全部下沉内核（Rust），应用层只做编排**；**编辑页组件边界
从 M1 起就保持干净**（壳与编辑页解耦是组件化的前置，事后改很贵——
边界纪律先行，Blueprint 化在 L2 落地）。auto-edit 对内核的诉求以
「本仓供料 → auto-lang 立上游计划」模式推进（PLAN-669 先例）。

### 4.2 内核路线（学 Zed 的三课，剥离协作一课）

1. **Rope + 摘要树，但去掉协作基因**（v2 修正）：Zed 的
   [Rope & SumTree](https://zed.dev/blog/zed-decoded-rope-sumtree) 本体
   是单编辑器性能件（叶存文本块、节点缓存长度/行数/点-偏移摘要，
   O(log n) 编辑定位），这层要；其 copy-on-write/线程安全的**动机**在
   我们这里是后台任务（解析/搜索/diff/保存）的快照隔离，不是多人并发
   ——所以**单写者模型**：主线程写、后台只读快照，不做 OT/CRDT/多编辑
   流合并。viewing-first 之下，**打开→首帧渲染→滚动**路径的优化优先于
   编辑路径的复杂度；编辑 API 从"整文本回读"改为**增量 delta**（§4.3）。
2. **增量一切**：tree-sitter 增量语法解析（高亮/大纲/符号索引共用一棵
   增量树——替代语言服务的轻量底座）；增量搜索索引；diff 增量重比。
3. **GPU 直渲**（[Zed: GPUI](https://zed.dev/blog/videogame-speed-ui-hardware-rendered-gpui)）：
   不自写 UI 框架——iced+wgpu 已是 GPU 路径，内核已做"只 shape 可见行"
   的视口虚拟化（Plan 629）；差距在帧预算纪律（§5 bench 门禁兜底）。

### 4.3 写路径重构：结构化编辑 API 第一等公民

现状 store 每 tab 持整文件字符串镜像（`tabs[i].src`），cut/paste/undo 后
`code_editor_text()` 全量回读（editor_store.at 中 5 处）；back `read_text`
整串交付。对大文件是结构性死罪，且与"编辑经 agent 命令发生"的定位直接
冲突。目标形态：

- store 只持 **buffer 句柄**（key/path/dirty/元数据），文本本体只活在
  内核 buffer registry；
- **统一 delta 协议**：人的击键、agent 的结构化写（区间替换/插入/删除）、
  undo/redo 走同一条增量事件流——人编辑和 agent 编辑在内核层无差别，
  这是"被驱动"的架构前提；
- back API 增加分块读（offset/limit）与结构化写端点；
- 大文件模式下 front 甚至不"拥有"全文——视口拉取。

这是 M1 的本仓主计划候选（对上游配套诉求：delta 事件与增量写 API）。

### 4.4 引擎与进程模型

- **默认 merged（进程内直调）**：性能主路径，维持 PLAN-003 裁定
  （pac 永不写 `api:`）。
- **split（HTTP）**：agent 驱动/自动化与联调形态，天然崩溃隔离。
- **a2r（原生 Rust 编译）**：standalone exe 交付与终极性能的依赖——
  当前 F-R1（server 模板硬编码 `api::Db`）未解，且 app 级转译路径
  （C/ninja）被裁定为脚枪。**M1 需要在 auto-lang 立项澄清独立 exe
  的官方打包路径**（解释执行打包资产，或 a2r 修复），这是 M 线交付
  形态的前置。
- 重活（解析/搜索/diff/大文件 IO）一律出主线程——iced 事件循环只做编排
  （单写者 + 快照隔离，见 §4.2）。

### 4.5 配置与扩展策略

- config-as-data：键位（已有 OS 键位层 `%APPDATA%/auto/keymaps`）、
  外观、行为均为数据文件；actions DSL 继续做三源绑定的单一事实。
- 无插件承诺（§1.3）；远期若开放，WASM 沙箱是唯一可接受形态。

## 5. 性能文化（M1 立即建立）

- `tools/bench/`：启动（冷/热）、打开文件（1/10/100/512 MB）、键入延迟、
  滚动帧率、内存、**diff 计时**（1/10/100 MB 同比对）——机器可复现脚本，
  结果入仓追踪。**探针独立于 desktop_mcp/MCP 链**（绕开 F-RV6 非确定）；
  启动链分解（进程 spawn / VM boot / 开窗 / 首帧各占多少）是第一产出。
- **门禁两档**：启动/首帧类"产品身份"指标硬门禁——回归即红、当天修
  （5ms 回归当天修便宜，累积到 M4 的 200ms 是重写）；滚动/内存/diff 等
  指标 M2/M3 期间**记账不阻塞**，M4 统一收口。缓冲区类指标在 rope 落地
  前标"架构阻塞"，不参与门禁（§2.1 解锁条件列）。
- **测量模式阶梯（预算效力分级，同日补注二）**：
  - **L0 日常（VM+merged）**：功能与结构回归；无绝对性能效力（解释执行
    + 每实例自付 iced/wgpu 初始化）。
  - **L1 结构探针（VM+RQ 预热）**：进程拓扑与阶段分解的**形状**可参考
    （app/渲染器分离后的相对占比），数值仍无效力。
  - **L2 性能模式（a2r+release+RQ 预热）**：**唯一有预算效力的模式**。
    一键脚本化（`tools/perf/`：RQ 启动编排 + a2r release 构建链 + 探针
    套件），周期长属预期——跑于里程碑、M4 收口、疑似回归时。
  - 日常防盲区靠**代理指标**（任何模式可读）：阶段时间戳插桩（进程起/
    逻辑 init/首帧请求）、编辑路径全量读检测、分配计数——结构回归在
    L0 就暴露，不等 L2。
  - 硬门禁只在 L2 数字上评估；L0/L1 数字永不入公开对比表。
- 公开对比：README 发布与 NP++/VSCode/Zed（打开/滚动）及 Beyond
  Compare（diff 计时）的同机对比表——"最快/最好比对"只有公开可复现
  才有说服力（Zed 的 performance 页面先例）。全部为 L2 数字。
- 前置修复：desktop_mcp 矩阵的工具链非确定性（F-RV6）必须先稳定，
  否则 bench 与功能矩阵互相污染归因。

## 8. 兄弟仓分工

- **auto-musk**（v2 升首位）：agent 产品线的 canonical 位——agent 人格、

  **旗舰应用 + 内核需求供料方 + 性能标尺**（669 模式放大版，diff 引擎
  供料是下一件）。

  交付为前置，现已可开工。战略关系待裁定（§9-Q1）。

  可参照（Zed 即 tree-sitter 作者的编辑器）。
